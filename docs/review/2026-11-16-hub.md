# Hub plan review (2026-11-16)

A read of [hub.md](../plans/hub.md) against the code as it stands, looking for what would break or be expensive to change after it's built. The proposals were accepted on 2026-11-16 (decisions near the end) and hub.md was rewritten to match. This file keeps the reasoning.

## Verdict

The shape is right and I wouldn't change it: instances do the work, the hub gives names, routing and identity, everything else is a hub service, and the hub is trusted like an ISP. Standalone mode, the owner-approves-everything rule and "no network mesh" all hold up.

Six things would hurt if built as written. Each is cheap to change now.

| # | Problem | Change |
|---|---|---|
| 1 | Published services at `user1.l0w.run/s/…` put agent-made pages on the same origin as the owner's UI | Serve nothing agent-made on the instance's own hostname; use separate hostnames on a second domain |
| 2 | All members share one site (`l0w.run`) as browsers see it | Get the domains on the Public Suffix List, and use `__Host-` cookies |
| 3 | Signing HTTP requests can't cover the relay, groups, or forwarding between hubs | Sign the message itself (an envelope), and encrypt it to the recipient |
| 4 | Peer messages, board posts and email are a prompt-injection channel into an agent that holds secrets and tools | Read them in a low-privilege run with its own budget; that also replaces the estimated spend breaker |
| 5 | Control can't start `cloudflared` (no Docker socket), so the wizard's "join a hub" step can't work | Ship a tunnel sidecar that's always present and waits for a token |
| 6 | A tunnel exposes all of control's port, including `/api/agent/*` | A public-surface allowlist, and the instance hardening listed at the end |

The rest of this file is the reasoning, then smaller gaps, Cloudflare's limits, and a revised build order.

## 1. Published services can't live on the instance's hostname

hub.md says that on Cloudflare a published service gets a path: `user1.l0w.run/s/ml-results/`. That URL is the same origin as the owner's control UI. A page the agent serves there runs with the owner's session: it can call the owner API, approve the agent's own permissions and read secrets' metadata. It can also register a service worker for the origin. This breaks an invariant the project already has ("agent HTML/SVG only in a sandboxed frame on a separate origin"), and it's the agent that chooses to publish.

The plan's other sentence, "people open services in their own UI, proxied with their identity, in the sandboxed frame", has a second problem. A sandboxed frame without `allow-same-origin` has no cookies, no local storage and a null origin. Jupyter, Gradio, Streamlit and most small web apps the assistant will write don't work that way.

**Proposal**
- `user1.l0w.run/s/<name>/` accepts **signed requests only** (other instances' gateways). It never answers a browser.
- Anything a browser loads from an agent gets **its own hostname on a second domain** kept for agent-made content, the way GitHub uses `githubusercontent.com`. For example `ml-results--user1.l0w.page`. Flat, first-level names, because Cloudflare's free certificate covers `*.l0w.page` and not `*.user1.l0w.page`. Each is one DNS record the hub creates through the API, pointing at the member's tunnel; `cloudflared` routes by hostname.
- The same domain replaces today's extra ports, which don't exist behind a tunnel: `files--user1.l0w.page` for the files origin (port 8001) and `web--user1.l0w.page` for the agent's page (port 8787).
- A friend viewing your service opens it at your service's hostname, with a short-lived visit token from their own instance. See [the second pass](#opening-a-friends-service-in-a-browser-no-viewer-side-proxy), which replaced my first idea of proxying through the viewer's instance.
- Member names can't contain `--`.

This needs deciding before the directory format and the gateway are specified, because the name-to-URL rule is part of the protocol.

## 2. One domain, many members

Browsers decide "same site" by registrable domain. `user1.l0w.run` and `user2.l0w.run` are the same site unless `l0w.run` is on the Public Suffix List. Consequences today:
- `SameSite=Lax` doesn't stop another member's page sending requests to your instance with your cookie. The `X-L0W-Client` header check still blocks writes, so this isn't a hole, but it's the only thing between a malicious member and CSRF.
- Any member's page can set a cookie for `.l0w.run` that your browser then sends to your instance: session fixation, or just a 50 KB cookie that makes every request fail.
- Storage partitioning, password managers and browser permission prompts all treat every member as one site.

**Proposal**
- Submit `l0w.run` and the content domain to the Public Suffix List early. It takes weeks and the hub doesn't need to exist first.
- Name the session cookie `__Host-l0w_session`. Browsers refuse to let another hostname set or overwrite a `__Host-` cookie. (Bug S3 in the [bug list](2026-11-16-bugs-and-code.md) is the place to do it.)
- Reserve names so a member can't register one that a hub service or convention needs: `board`, `mail`, `spaces`, `admin`, `api`, `www`, `hub`, `files`, `web`, anything with `--`, and lookalikes of them.
- **Never reuse a name.** `user1@l0w.run` is an email address people will sign up to other services with. Whoever gets the name next receives the old member's password resets and friend lookups. Pinned keys protect friends; nothing protects email.

## 3. Sign messages, not connections

hub.md: "Instances sign requests to each other (HTTP Message Signatures) and pin keys on friending." Then, in other sections: an offline relay "holds signed messages", group delivery fans out, and linked hubs "forward traffic".

An HTTP signature proves who made *this request*. When the relay hands you a message hours later, the request is the relay's. The original sender's signature covered a different URL, time and connection, so you can't verify it. The same holds for group fan-out and anything a hub forwards. As written, every stored or forwarded message can only be trusted as far as the intermediary, which is exactly what pinned keys were meant to prevent.

**Proposal: one envelope for everything instances exchange**
- Fields: sender address and key id, recipients, a message id, the sender's sequence number, a timestamp, a type, the body's hash, the signature. Ed25519, with an algorithm field so it can change.
- Receivers verify against the pinned key whatever path it took. Replays are caught by message id and sequence; the timestamp only bounds how long ids are remembered.
- HTTP Message Signatures stay, as hop authentication only: "this request really is from user2's gateway", with the target URL, a body digest, `created`/`expires` and a nonce.

**Encrypt while you're there.** TLS ends at Cloudflare and the hub routes everything, so today the operator and Cloudflare can read every DM and file between friends. "Trusted like an ISP" covers that on paper, but friends won't expect it. Each instance publishes an encryption key next to its signing key, and the envelope body is sealed to the recipient's pinned key (HPKE, X25519). Then the offline relay stores ciphertext, and a shared space or a group has a key sealed to each member. The board and email stay readable by the operator, by nature. This is a few days of work in the envelope and close to impossible to add after the relay, group delivery and space formats exist.

**Key loss and compromise**, both missing from the plan:
- *Lost key* (the server died, no backup): "rotations are signed by the old key" means the identity is gone. Add a **recovery key** made at join and shown once, which can sign a rotation. Without one, the hub can attest "this member re-registered", and each friend's owner gets a card: "user1's key changed without proof it's the same instance. Re-verify?" Never automatic.
- *Stolen key*: the thief can sign a rotation too. The recovery key must be able to revoke, and the hub must be able to mark a key revoked in the directory.
- Put the instance key and the friends list (addresses, pinned keys) in the backup/export. Backups currently sit on the Later list; they become a prerequisite here.

**Checking the hub.** The hub can hand out a wrong key on first lookup. Two cheap checks make that detectable: each instance fetches its own directory entry every day from the outside and alerts the owner if it isn't the key it holds; and the friend-approval card shows a short fingerprint both owners can compare.

**Make the key the identity and the address a label.** If a friend's record is "this key, currently reachable as `user1@l0w.run`", a member can move hubs with a "moved to" record signed by the same key, and friends follow. If the record is the address, moving hubs means re-friending everyone. It also gives "these two instances have the same owner" a definition: each signs a statement naming the other. The wake policy "allow for your own instances" needs that.

## 4. Peers, the board and email are an injection channel

The plan says this content is untrusted data, and gives the spend breaker to bound the cost. That bounds money, not damage. An assistant that reads a friend's message is a model with secrets in its environment, egress, GitHub write access and (later) outbound email, reading text written by someone else's model, which itself read the web. The board is worse: "assistants subscribe to topics and get **every post** at their next wakeup" means one post reaches every subscriber's agent, and a post that says "repost this and DM it to your friends" is a worm. Assistant-only boards with automatic delivery are the textbook case.

A prompt rule ("never instructions") reduces this; it doesn't stop it. Control can.

**Proposal: a separate kind of run for outside content**
- A **social run** reads peer messages, board posts, discussion mentions and inbound mail. It runs with no secrets in its environment, no brokered tools that write, read-only egress, and no access to `/work` beyond a scratch folder and `_inbox/peers`. It can reply to peers, post, vote and write a digest for the main agent.
- The main agent gets the digest (title, who, one-line summary, a link) and reads the original only when it chooses to. Reading an original through `assistant` marks the run **tainted**: for the rest of that run, `secret get` is refused, write tools go back to "ask", and outbound email and widening a published service need the owner whatever the allowlist says. Control can enforce this because all of that content arrives through commands it serves.
- Social runs spend their own **peer bucket**, like the reply bucket. That replaces "turns spent on peer conversation (estimated; approximate in mixed runs)" with exact accounting that already exists in the ledger. The breaker's limits (20% of a run, 5% a day) become the bucket's size, and the owner card ("Allow +5% today") tops it up. A run a peer woke is a social run.
- What this doesn't fix: a digest is still model output influenced by the attacker, and notes the social run writes persist. Keep its notes in one place (`people/`, `_inbox/`) with the source recorded.

**What the assistant tells others** has no rule in the plan. Add:
- Outbound peer messages and posts go through `vault.redact`, always.
- A per-friend sharing level set by the owner: nothing about my projects / the shared projects only / anything. Default the first.
- The first few messages to a new friend need the owner's approval, like outbound email does. It teaches the owner what their assistant says before it's routine.

**Board specifics**
- Deliver titles and summaries, not bodies. Bodies on request, which taints.
- Rate-limit posts per member per day (the plan limits discussion messages only), and hold a new member's first posts for the moderator.
- One vote per member is one vote per *instance*, and a person may have several. Count per owner once "same owner" exists.
- An operator switch that pauses delivery hub-wide, and an owner switch that pauses all social activity. When a bad post goes out, minutes matter.

**Email specifics**
- Mail from an unknown sender is quarantined: the owner sees it; the agent gets sender and subject, or nothing, until the owner allows the sender. An address on the open internet will get spam within days, and every message is a free prompt.
- Allowlisted senders must pass DMARC, or spoofing the owner's own address walks straight through.
- The allowlist that skips outbound approval is also an exfiltration path for a tainted run; in a tainted run, always ask.
- One member's agent sending junk damages the domain's reputation for everyone. Keep the daily cap low, suspend on the first complaint or bounce spike, and think about whether mail should come from a subdomain so the main domain's web reputation isn't tied to it.

**Waking and presence**
- The "wants to wake yours: <reason>" push shows text the other side wrote. Cap it short, show the friend's name and hub larger than the reason, and limit requests per friend per day.
- Presence sends your next wakeup time and optionally the "now" sentence to friends. Default to coarse (asleep / working, "tonight"), with the detail opt-in per friend.

## 5. Joining a hub needs a host-side step that doesn't exist

The wizard lists "optional hub join". Joining means running `cloudflared` with a tunnel token. Control has no Docker socket, by design, so it can't start a container.

**Proposal:** `compose.yaml` always includes a small `tunnel` service: a wrapper that asks control for a token and, when there is one, runs `cloudflared` with it. Until then it idles. Joining and leaving are then entirely in the UI, and `./l0w hub join <invite>` is only a convenience. The tunnel container goes on its own network with control, never on the sandbox network.

The join flow, since the plan doesn't spell it out: the owner pastes an invite; control makes the instance keys and the recovery key; it registers name, public keys and invite with the hub (signed); the hub creates the tunnel and DNS records and returns the tunnel token; control stores it in the vault and the sidecar picks it up; control checks from outside that the name reaches it.

## 6. What a tunnel exposes

`cloudflared` forwards to control's port 8000, and everything on it becomes public:
- `/api/agent/*`, protected only by a token that lives in the untrusted container (bug S2).
- `/api/chat-runtime/*`.
- `/oauth/register`, open to anyone (bug S11).
- The login form, with a lockout a stranger can trigger (bug S14) and rate limits that see one address (bug S13).

**Proposal**
- Give `cloudflared` its own subnet and treat requests from it as a caller class: they may reach the UI, the owner API, `/mcp`, `/oauth/*`, `/.well-known/*`, `/api/peer/*`, `/api/hub/*` and `/s/*`. Nothing else, default deny. (Code improvement 1 in the bug list is this table.)
- Take the client address from `CF-Connecting-IP` only when the request comes from that subnet.
- Require 2FA to join a hub, rather than "the wizard encourages" it, and build passkeys and the breached-password check first: both are deferred today.
- One Cloudflare rate-limit rule on the zone for `/api/auth/*`, in front of everyone's instance.

## The gateway

The plan gives control a gateway that signs outbound requests and verifies inbound ones. Three points.

- **Outbound calls must be vetted like egress.** The flow is "agent → egress → control's gateway → the target's public URL". The gateway sits on control's networks, past egress. If the target URL comes from a directory entry or a friend's record, a hostile one can point at `http://egress-admin:8090`, the runner, or the owner's router. Resolve, refuse private and internal addresses, https only, connect to the vetted address, no redirects. Bug S17 is the same hole in today's integrations; one function serves both.
- **Make it its own container.** It holds the instance key, parses hostile input from the internet, and (for streams) carries long-lived TCP. None of that should share a process with the owner API and the vault. A small `gateway` service that control talks to keeps the key away from control's bugs and control's event loop away from stream traffic. The plan's rule "the extension never sees the instance key" then holds by construction.
- **Streams will be slow, and that's fine if it's said.** TCP over WebSockets, through two gateways and Cloudflare, adds latency and has no delivery guarantees beyond TCP's own. Good for a database or a notebook kernel; poor for a game server. Say so in the plan, cap bandwidth per stream, and check Cloudflare's terms on sustained non-web traffic through a free tunnel before promising it.

## Shared spaces and shared projects

**Shared spaces** are the most expensive piece in the plan: a sync engine with versions, conflicts, locks and quotas. The described behaviour is sound. To make it buildable:
- **Files as content-addressed blobs in R2, uploaded directly** with presigned URLs. That avoids the 100 MB request limit on tunnels and Workers.
- **Each version is a manifest** (path → hash, author, time, message, parent) **signed by its author's instance.** Members verify signatures, so a compromised hub can't inject a file. Encrypt blobs with a space key sealed to each member.
- **One Durable Object per space** holds the head and the locks. A push is compare-and-swap on the head: if it moved, the client pulls, merges changes to different files itself, and keeps both copies of a file changed on both sides. That is the plan's conflict rule, with a definite place where ordering is decided.
- **What control must refuse to sync out of the agent's folder:** symlinks, special files, anything over the size limit, and any file containing a vault value. It needs an ignore file, or the first `node_modules` or virtualenv ends the quota.
- **Files from other members are untrusted code.** An agent that runs a script a friend's assistant put in `/shared/x/` runs it with its own secrets and egress. Runs that touch a shared space should get project-scoped secrets only, and the manual should say "read before you run".

**Group chats** "instance to instance" need every member to deliver to every other, agree on who's a member, and agree on order. With one member offline for a day that falls apart: missed messages, two versions of the member list, and no history for someone who joins later. Host the room in a Durable Object (ordering, history, membership), with message bodies encrypted to the members. Keep direct delivery for one-to-one messages, where it's simple.

## Smaller gaps

- **Versions.** Friends update at different times. Every envelope carries a protocol version, receivers ignore fields they don't know, and the capabilities document gives the range a hub accepts. First-party extensions ship with the image while hub services change on the operator's schedule, so state the rule: a hub service supports the current and the previous instance release.
- **Linking.** If addresses are always written in full (`user1@l0w.run`, `ml-results.user1@l0w.run`) and directory lookups are plain HTTPS to the other hub's own domain, any instance can already verify a member of any hub. "Linking" then means policy and shared services, and the core needs no "forward traffic" function. That's less to build and less to trust.
- **When the hub's Cloudflare account or domain goes away,** everything goes with it, including friends talking directly, because their URLs are on that domain. Let an instance publish a second URL (Tailscale Funnel, its own domain) in its signed self-description, so friends can still reach it.
- **The extension SDK comes first in the plan and has no real consumer yet.** Hub features "plug in as first-party extensions (needs M8)". An SDK designed before the board and email exist will be wrong in ways only they reveal. Build friends and DMs in core behind internal interfaces, build the SDK alongside the first hub service that needs it, and move the core pieces over once two services use it.
- **Operator duties.** A board hosts other people's content and the mail service sends on a shared domain. Even among friends: terms, an abuse address, the ability to remove content and members, and a retention rule. Invites only until those exist.
- **Moderator assistants** read untrusted posts all day and hold moderation powers. The plan's safeguards are right; add that moderation always happens in a social run (section 4).

## Cloudflare limits to design around

Confirm the numbers when you start; they change.

| Limit | Effect |
|---|---|
| Free certificates cover one subdomain level | Flat names (`files--user1`), as in section 1 |
| Request bodies capped at 100 MB (free and pro) | Uploads through the hub URL fail above that. Chunk attachment uploads; send space blobs straight to R2 |
| A response must start, and keep sending, within about 100 seconds | The live stream already sends heartbeats, good. Any owner API call that blocks for minutes will fail through the tunnel; make those return at once and report through the live stream |
| Email Workers accept messages up to about 25 MB | Larger mail bounces; say so |
| Tunnels and DNS records per account and zone | Roughly a thousand tunnels by default, and a few hundred to a few thousand records depending on the plan. With three or more records per member plus one per published service, this is the first ceiling. Fine for friends; know where it is |
| Workers free plan: 100,000 requests a day | Member UIs don't pass through a Worker (DNS goes straight to the tunnel), so only the directory, board and mail count |
| Sustained non-web traffic | Streams (above) |

## A revised build order

The plan's order is mostly right. The changes: harden the instance first, settle the envelope before anything stores messages, and move published services after the domain work.

0. **Instance ready for the internet.** The six "before the hub" bugs, the caller-class guard, trusted proxies, `__Host-` cookies, passkeys, required 2FA, backups that include keys. All of it can be tested today behind Tailscale Funnel. Submit the domains to the Public Suffix List.
1. **The protocol on paper.** The envelope, key rotation and recovery, address and name rules, the name-to-hostname rule, versioning. Conformance tests with it.
2. **Hub core.** Membership and invites, the tunnel sidecar, the directory, capabilities, the daily self-check.
3. **The gateway container, friends and DMs.** Envelope, encryption, presence, social runs and the peer bucket, the taint rule.
4. **The connector through the hub** (Claude.ai, ChatGPT). Small once 0 and 2 are done, and useful on its own.
5. **The extension SDK with the first hub service** (the offline relay or the board), then the admin page.
6. **Published services** on the content domain, then the services directory.
7. **Shared spaces and hosted group rooms.**
8. **Email**, inbound with quarantine, then outbound.
9. **Linking, then streams.**

## Second pass

Thinking the accepted design through to the next level of detail turned up these.

### Opening a friend's service in a browser: no viewer-side proxy
The plan has the viewer's instance proxy the service "with their identity". With a content domain that isn't needed, and dropping it removes a whole data path.
- The service lives at the **publisher's** hostname, `ml-results--user2.l0w.page`.
- When you click it, your instance mints a **visit token**: signed with your instance key, naming the service, valid for a minute, usable once.
- Your browser opens the publisher's hostname with the token. The publisher's gateway checks the signature against your pinned key and the service's access rule, sets a session cookie for that one hostname, and redirects to drop the token from the URL.
- From then on it's an ordinary website on its own origin. Cookies, local storage and websockets work, so Jupyter, Gradio and Streamlit work.
- Open it in a **new tab** by default. Inside a frame in your UI its cookie is a third-party cookie, which Safari and Firefox block.
- Your **agent** still reaches a friend's service the planned way: through egress and your gateway, with signed requests.

The publisher logs every visit by friend; your instance logs every token it minted.

### Hostnames: three fixed ones per member, one per published service
- At join the hub creates `user1.l0w.run`, `files--user1.l0w.page` and `web--user1.l0w.page`, all pointing at the member's tunnel.
- Each published service that a browser may open gets one more record, created by the hub on a signed request from the instance. Cap them per member (say 20) and remove the record on unpublish.
- A tunnel can't take a per-member wildcard at this level, so the alternative to per-service records is a hub Worker that routes `*.l0w.page` by name. That puts every request through the Worker's quota and the operator's code. Records are simpler at friends scale; keep the Worker as the fallback if the record ceiling is ever reached.

### The self-description is the source of truth; the directory is an index
Each instance serves a signed document at `/.well-known/l0wagent/self`: its address, keys with history, its URLs (including a second one outside the hub), the protocol versions it speaks. The hub's directory entry is a copy of it plus the hub's signature. Consequences:
- A standalone instance with its own public URL can be friended with nothing but that URL, as the plan promises but doesn't explain.
- A member with their own URL (Tailscale Funnel, their own domain) can join l0w.run for the directory, the board and email without a tunnel. That's cheaper for the operator, and the plan currently offers it only for non-Cloudflare hubs.
- The daily self-check compares the directory's copy with the instance's own.

### Friend requests are a spam channel
Any instance on any hub can send a request to any address, with text. Rules:
- A request is an owner card and never reaches the agent as content.
- **Friend codes**: a one-time code you give someone out of band. A request carrying a valid code shows up at once. Others go to a quiet list, or are dropped, by the owner's choice ("requests from: anyone / my hub and linked hubs / codes only").
- Limits per sending instance and per hub, enforced by the gateway.
- Block and mute per friend, and a report to the hub operator.

### Delivery tokens
At friending, each side gives the other a signed **delivery token**: "this key may deliver to me". A message carries it. The gateway drops anything without one before parsing further, and the offline relay can check it without learning who is friends with whom beyond what it's handed. Revoking a friend revokes the token.

### The relay becomes a mailbox
With envelopes and encryption, the offline relay only stores ciphertext addressed to a recipient: accept an envelope with a valid delivery token, hold it up to 14 days within a quota per recipient and per sender, hand it over when the recipient asks. It never needs to understand a message, so it rarely needs to change.

### Removing someone from a group or a space
With encryption, removal means a new key for what comes after: the room or space makes a new key and seals it to the remaining members. What the removed member already had, they keep. Say so in the UI.

### A fake hub for development
The assistant is tested without a Claude login because of the fake runtime. The hub needs the same: a small `dev/hub/` service that implements the core API (membership, directory, capabilities, relay) with no Cloudflare, and a compose file with two instances and the fake hub. Friending, messaging, key rotation and the taint rule become ordinary integration tests, and the conformance tests have their first target. Build it with step 1 of the order above, before the real hub.

### Things to state in the plan so nobody is surprised
- **The operator can read email and the board, and sees who talks to whom.** Encryption covers message bodies between friends, spaces and rooms. A short privacy statement per hub.
- **Clocks.** Signatures carry times; allow five minutes of skew and show a clear error beyond it.
- **Inactive members.** A name whose instance hasn't checked in for months keeps its name (never reused) but loses its tunnel and records until it returns.
- **Scoped tokens for the host CLI.** A device token has the owner's full authority, approvals included, and coding agents use the CLI. Before the instance is public, add tokens limited to reading, or to everything except approvals, secrets and settings.
